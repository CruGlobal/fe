# Internationalization: Focus Areas

fe localizes in two separate ways, and they don't share a store:

1. fe's own fixed text (notices, buttons, reference instructions) uses gettext through
   `gettext_i18n_rails`: `_("...")` in views and code, msgids in `locale/app.pot`, translations in
   `locale/{es,fr,pt}/app.po`.
2. Form text written in the builder (question labels, tips, paragraph content, choices, rating
   labels, page labels) is stored per language in YAML-serialized hash columns keyed by
   `Fe::LANGUAGES` codes. Each question sheet lists the languages it offers in
   `Fe::QuestionSheet#languages`.

Rails I18n (`config/locales/en.yml`) only carries date and number formats.

**gettext strings**

- Respondent- and reference-facing text in `app/views/fe/answer_sheets/`, `answer_pages/`,
  `submit_pages/`, `reference_sheets/`, `references/`, `reference_pages/`, and
  `app/views/fe/questions/fe/` goes through `_()`. The builder (`app/views/fe/admin/**`) is mostly
  English literals today
- Interpolate after the lookup:
  `_("If you have any questions or concerns, email us at %{email}") % { email: Fe.from_email }`.
  Never build the msgid with `#{}`; it then matches no translation
- Look for: new respondent-facing literals in views, `.js.erb` responses, controller `flash`
  messages, or JS `alert(...)` text that skip `_()` (some existing ones do; don't add more);
  rewording an existing msgid (it orphans the es, fr, and pt translations, so update
  `locale/app.pot` and every `app.po` together); a new msgid that isn't added to `locale/app.pot`
  and the three `app.po` files (an empty `msgstr ""` falls back to English, which is fine); markup
  or `raw` inside a translated string

**Per-language form text**

- Translatable columns: `Fe::Element` `label_translations`, `tip_translations`,
  `content_translations`; `Fe::ChoiceField` `rating_before_label_translations`,
  `rating_after_label_translations`, `rating_na_label_translations`; `Fe::Page` `label_translations`
- Readers take a locale and fall back to the base column when the translation is blank:
  `label(locale = nil)`, `content(locale)`, `tooltip(locale)`, `rating_*_label(locale)`,
  `choices(locale)`. Views pass `session[:locale]` (`element.label(session[:locale])`,
  `page_link.label(session[:locale])`)
- A new translatable field needs every piece: a `text` column migration; the `serialize ... Hash`
  call with the `Rails.gem_version < "7.1.0"` branch; a `<field>(locale = nil)` reader with a
  `.present?` fallback; `{<field>_translations: Fe::LANGUAGES.keys}` in `element_params` or
  `page_params`; builder inputs that loop `question_sheet.languages.select(&:present?)` and label
  each with `Fe::LANGUAGES[language]`; and views that pass `session[:locale]`
- Look for: a respondent view calling `element.label` with no locale; a reader that returns a blank
  translation instead of falling back (`Fe::Page#label` uses `||`, which keeps an empty string;
  new readers follow `Fe::Element#label`'s `.present?` form); translated text rendered differently
  from its base text

**Languages and locale selection**

- `Fe::LANGUAGES` (`{ 'es' => 'Español', 'pt' => 'Português' }` in `lib/fe.rb`) drives the
  builder's language picker and the permitted translation keys. English is the base columns, not a
  key. `locale/fr/` has gettext strings but `fr` is not in `Fe::LANGUAGES`; don't assume the two
  lists match
- `Fe::ApplicationControllerConcern#set_locale` (host apps include this concern) sets
  `session[:locale]` from `params[:locale]`, then the `Accept-Language` header, then
  `I18n.default_locale`, and, when `@answer_sheet` is already loaded, resets to the default if the
  sheet's `languages` doesn't include it. `Fe::AnswerSheetConcern#languages` intersects the languages
  of all the sheet's question sheets. The save path stores the locale on the sheet
  (`@answer_sheet.update(locale: session[:locale])`); reference sheets have their own `locale`
  column
- Look for: Symbol vs String locale comparisons (`I18n.default_locale` is a Symbol; `Fe::LANGUAGES`
  keys, translation hash keys, and `languages` entries are Strings); a language added to
  `Fe::LANGUAGES` with no `locale/<code>/app.po`; code that assumes one question sheet per answer
  sheet when picking a language

**Dates**

- The date picker format is `Fe.date_format` (jQuery UI syntax, default `'yy-mm-dd'`, compiled into
  `fe.common.js.erb`), and the server parses `'%Y-%m-%d'`. Display formats come from
  `config/locales/en.yml`. Look for: a localized display format leaking into what the form posts

**Checklist**

- [ ] New respondent-facing text uses `_()` with `%{}` placeholders
- [ ] `locale/app.pot` and `locale/{es,fr,pt}/app.po` updated for added or reworded msgids
- [ ] A new translatable field has its column, `serialize` call, reader with fallback, permitted
      keys, builder inputs, and views that pass the locale
- [ ] Respondent views pass `session[:locale]` to every translatable reader
- [ ] Locale comparisons are String to String
